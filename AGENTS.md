# Agent Instructions

Before editing the project, inspect the current workspace and read this file. Follow the project structure, dependency-layer, naming, and source-file organization rules documented in [`app/docs/structure.md`](app/docs/structure.md), and follow the UI design and icon conventions in [`app/docs/architecture.md`](app/docs/architecture.md).

Preserve existing behavior and unrelated user changes. Make focused source edits rather than rewriting whole files or removing code merely to reduce line count. Do work one item at a time from easy to hard. Do not commit, push, or build unless explicitly asked. Run lint and tests together after the implementation is complete rather than repeatedly invoking Gradle for lint during the work.

## Isolated and offline agent environments

Some agents run in sandboxes with no Internet access and may have no JDK, Android SDK, emulator, Gradle distribution, or cached dependencies. Follow these rules when working in such environments:

- Do not install/download toolchains or dependencies, invoke `sdkmanager`, or try network workarounds. Do not repeatedly run Gradle after confirming a required toolchain/artifact is missing.
- Diagnose available prerequisites first (`java -version`, whether `$ANDROID_HOME`/`$ANDROID_SDK_ROOT` exists, cached Gradle wrapper/distributions and dependencies, and repository scripts). Do not assume a path or environment variable exists.
- If prerequisites are available, prefer offline Gradle mode when appropriate. If the JDK, Android SDK, wrapper distribution, or required dependencies are absent, stop build attempts and continue with source inspection and checks that can run offline, such as `git diff --check`, local scripts, and static review.
- Report each verification precisely: distinguish passed, failed, and not run; state which missing prerequisite blocked a check. Never claim a build, lint, or test passed if it was not executed successfully. Add tests where appropriate even when they cannot run in the sandbox, and provide the exact command for a fully provisioned environment.
- Environment limitations are not a reason to guess APIs or make broad speculative changes. Inspect existing source/tests, keep changes narrow, and document remaining verification gaps.

## Architecture rules

Treat these as mandatory constraints; `app/docs/structure.md` contains the full package map and supporting details.

- **Dependency direction:** `shared` ← `integrations` ← `database` ← `features` ← `navigation` ← `appwiring`. A layer may depend only on layers to its left. `shared/` and `integrations/` must never import `database/` or `features/`; `database/` must never import `features/`; feature packages must not import each other. `home/` is a feature under `features/`, not a peer layer.
- **Place code by responsibility and usage.** Keep code in the closest layer that uses it. Move code to root `shared/` only when it is genuinely reused across features/layers; external API and protocol communication belongs in `integrations/`; Room databases, DAOs, entities, migrations, database-backed repositories, and their storage mappers belong in root `database/`. Keep preferences and reusable state primitives in `shared/storage/`. Helpers prepare inputs or interpret outputs and must not import `integrations/`. Models must not import UI, logic, or helpers.
- **Features are vertical slices, not screen registries.** The project uses a UI-First Clean Architecture–inspired, feature-first organization: a `features/<name>/` package represents a user/business capability and owns its presentation, application workflow/use-case coordination, and feature-specific state/models. It can contain multiple screens, components, and logic that are not tied to a single menu destination. `FeaturesScreen`/`AppMenuScreen` entries describe UI exposure; they do not define the feature boundary. The project uses `logic/` and `model/` rather than a canonical `domain/`/`data/` split, so classify files by responsibility and dependency direction rather than folder names alone.
- **Within a feature:** UI may depend on logic and model; logic may depend on model; model must not depend on UI or logic. `ui/` contains Compose rendering and user interaction, `logic/` contains ViewModels/coordinators/feature workflows and must not contain `@Composable` or import `androidx.compose.material3`, and `model/` contains feature-specific data/state types. Not every feature needs all three folders. Sub-features must not import each other; their shared code belongs in that feature's `shared/`.
- **Navigation:** transitions between screens go through callbacks wired in `navigation/AppNavigation.kt`, not direct imports of another screen.
- **File and component naming:** use PascalCase for Kotlin source files and Compose components. A UI file should normally match its primary public composable/type. Follow the component-role naming table in `app/docs/structure.md`; do not use screen, drawer, sidebar, sheet, and dialog names interchangeably. When renaming, update filenames, declarations, imports, navigation, previews, tests, and the structure map together.
- **Shared Compose naming:** prefer the shortest meaningful name, including the native Compose name when callers only need the shared variant. If a caller genuinely needs both a shared component and the corresponding native Compose primitive, give the shared component a distinct, purpose-specific name (for example, `ToolSwitch` alongside `Switch`) rather than resolving the collision with import aliases or generic `App`/`Shared` prefixes. Keep native primitives when they serve a different purpose. Aliases inside a shared component implementation to call the underlying Compose API are permitted.
- **Appearance and UserProfile are shared UI policies:** every component whose rendering responds to Appearance (theme, AMOLED, component transparency, etc.) or UserProfile (profile image/background and its opacity) must obtain that rendering policy from reusable `shared/` theme helpers/composables, not reimplement preference-specific colors, alpha, borders, images, or modal surfaces in individual features. Use `prominentContainerColor`/`Border`, `nestedContainerColor`/`Border`, `appearanceContainerColor`/`Border`, `modalContainerColor`, `ProfileBackground`, and the shared sheet/dialog/menu components as appropriate. Preserve feature-specific layout and semantic states; they may use native Compose primitives when those do not duplicate shared appearance behavior. New settings-dependent rendering rules belong in `shared/` once, with all consumers referencing them; never override the alpha of a shared appearance color with a hard-coded constant (use its `opacityBoost` where extra contrast is intended).
- **ChatAppBar exception:** keep the scrim only in the ChatAppBar surface, colored `MaterialTheme.colorScheme.background` to match the light/dark/custom theme, from 60% opacity at the top of the status bar to 0% at the bottom of the app bar. Its gradient is independent of Appearance component transparency and UserProfile photo transparency. The overlay must render above scrolling chat content but behind app-bar controls; never change the opacity or composable implementation of scrolling text, messages, or media blocks to achieve the effect.
- **File size:** aim for 500 lines or fewer per source file, including blank lines and comments. This is a soft limit: split only when it improves cohesion and avoids needless fragmentation.
- Before moving code or changing package structure, inspect callers, imports, tests, and package references. Preserve behavior and unrelated changes; do not create duplicate implementations to avoid updating references.

## Language and localization

- English is the canonical source language. Keep its user-facing text and documentation complete and up to date; adding or updating English alone is always allowed.
- For non-English translations, either add or update **all supported non-English locales** consistently in the same change, or add/update **none** of them. Never add or update only some non-English languages, even if several are changed together. Do not let AI arbitrarily select a subset of languages for translation. If all supported locales cannot be handled in the same change, leave non-English translations untouched and defer them to a coordinated localization change.
- This policy does not rank non-English languages by importance. When localization is undertaken, all supported non-English languages must receive equal consideration, comparable completeness, and feature parity. Translations should be natural and accurate for each locale, not literal word-for-word copies.
- Keep source identifiers, technical documentation, code comments, and maintainer-facing project text in clear, consistent English unless a file or task explicitly requires another language.

## Text input and IME behavior

- **Human-readable text fields** (chat messages, prompts, instructions, titles, display names, labels, folder names, descriptions, and natural-language search queries) must auto-capitalize the first letter using sentence capitalization (`KeyboardCapitalization.Sentences`, the default in `OutlinedTextField` and `HeaderNameField`) and preserve normal IME composition.
- **Non-prose / literal input fields** (URLs, API keys, tokens, secrets, passwords, model or resource IDs, hostnames, file paths, shell commands, HTTP header names/values, JSON/code/template literals, and numeric values) are the only text fields that should omit auto-capitalization: use `KeyboardCapitalization.None`, disable autocorrection/suggestions (`autoCorrectEnabled = false`), and disable IME text composition (for example with `KeyboardType.Password` paired with `VisualTransformation.None` when plain text should remain visible, or `KeyboardType.Number` for numeric inputs) so keyboards deliver raw literal input without IME composing transformations.
